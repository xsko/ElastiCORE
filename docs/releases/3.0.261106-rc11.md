The eleventh release candidate of 3.0: `@deleted` for a delete that keeps the row, `@stamp` for when a lifecycle
entered a state, a richer metric filter, `@template` lists of the fields a DTO takes, and guides that say where each
feature works.

### New features

- **`deletedAt: timestamp @deleted` - a delete keeps the row, with when, and no read finds it again.** JPA: the
  entity gets Hibernate's `@SQLDelete`, so the delete is still JPA's remove and `@PreRemove`, the lifecycle's delete
  guard and the invariants run as before; the repository's `findById`, `existsById`, `findAll` (plain, sorted, paged)
  and `count`, the search, and a collection of such rows leave deleted rows out. A row that names a deleted one by a
  to-one relation still reads it (an order line keeps its product). MyBatis: the deletes are UPDATEs and every
  generated statement reads the live rows. The column is written by the delete only - never by a request, an insert
  or an update - and a deleted user cannot sign in. The build stops, with the reason, where a delete would still
  remove rows outright (members of the aggregate or a cascading relation that are not `@deleted` too), and for two
  `@deleted` fields, a type other than `datetime` / `timestamp`, the key, a composite key, a JPA key the request gives
  without `@jpa:Version`, an `@embeddable`, a `@rollup` entity or a single-table hierarchy. With `mapping: xml` it
  works on Spring Boot 4 (Hibernate 7 reads `<sql-delete>` and `<sql-restriction>` from orm.xml, which the generated
  file then uses) and stops the build on Spring Boot 3, whose Hibernate ignores them. The 2.x-compatible output writes
  no such delete and warns. Not generated: restoring a row, and the filter in queries you declare yourself.
- **`shippedAt: timestamp @stamp(SHIPPED)` records when a lifecycle entered a state.** The command that moves the
  row into the state sets the field after the move, on every entry; a refused command stamps nothing.
  `@stamp(fee.REFUNDED)` names the lifecycle where two have the state, `@stamp(SENT, CANCELLED)` takes several, and
  `timestamp`, `datetime` and `date` fields are filled with the matching `now()`. The field is the lifecycle's: read-only
  in the DTO and the TypeScript client. JPA and MyBatis, Java and Kotlin, under the DDD and hexagonal rules; a state no
  move enters, or one two lifecycles share unnamed, stops the build.
- **A metric's filter takes `in (...)`, `not in (...)`, `or`, parentheses and `not (...)`, and
  `count(distinct Entity.field)` counts different values** - all forms of the Ossie SQL the export writes. Each listed
  value is checked like a single one, and a line that cannot be read is dropped with a warning that quotes it. As in
  SQL, `!=`, `not in` and `not (...)` leave out a row whose field is null.
- **`@template(Order[note, deliveryDate], Customer)` names the fields a DTO takes** of a model, instead of removing
  the others with `--`; a field added to the entity later stays out of the DTO until it is listed. Without brackets a
  model is copied whole, as before, in the 2.x generator, the compatible output and the 3.0 code alike. A name the
  model does not have, a relation with no field holding its id, a list on a search DTO and similar mistakes stop the
  build. A list without the key is not taken as the DTO of the entity's service and controller.

### Changes

- **The guides mark where a feature works.** A section whose feature is limited starts with `> **Works in:** … ·
  **Not in:** … (stops the build | warning | not generated)` - 58 sections, in English and Korean. Sentences that said
  the opposite of the code are corrected, notably: `testCode: "true"` writes a service test for 2.x code and Kotlin
  only, not for the v3 Java bundles; `publisher.rules` left out follows the build's architecture and language (layered
  Java: `jpa-springboot-v3`); `@formula` is not searched under MyBatis; `@jsonSerialize(using=…)` is written by no
  output. The pet store's guide page has a table of where the DSL it uses works.

### Compatibility checks

- The 2.x-compatible output is unchanged for a model that uses none of the new features. `elcoreRulesCheck -Pstrict`
  reports 158 MATCH / 0 DIFF / 2 ACCEPTED, and `elcoreTreeCheck` 239 files with 0 differ / 0 missing / 0 extra - one
  more artifact and file than rc10, from the reference project's new `EmployeeContactDTO @template(Employee[...])`.
