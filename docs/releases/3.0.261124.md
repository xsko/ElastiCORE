This release carries **two security fixes** for the 3.0 code; upgrading is recommended:
- a search could be sorted by a value its response does not show, which gave that value's order away
- under MongoDB, an `html` field on a member a document embeds was stored as sent, scripts included

It also renames the merge base `.elasticore/cache` to `.elasticore/generated-base.zip` (an existing project is moved
by its next build), keeps a hand-written member's Javadoc with it in the merge, makes the warning for rules the
selection does not carry give advice that fits, and adds three groups to `testCode: "contract"`.

If you use the ElastiCORE agent kit, update it to 1.1.0 or later first: older kits know the merge base only by its old
name.

### Security fixes

- **A search sorts only by what its response shows** (#304). The 3.0 search turned every `sortCode` / `sortColumn`
  term into a sort unchecked (JPA), or checked it only against the columns it can sort by (MyBatis, MongoDB), hidden
  ones included. A sort on a value the response leaves out still tells that value's order: e-mails, card numbers,
  password hashes. With rows of one's own to sort among, the order gives the value itself away.
  - Each 3.0 search DTO now lists what its sort may name (`SORTABLE_PROPERTIES`, `sortableProperties()`), and the
    runtime's new `SortCheck` refuses any other term with 400 `no-such-property` before the query is built. The same
    goes for `sortColumn`, the export (`POST .../export`) and every other call of `findBySearch` with a search DTO.
  - What may be sorted by: a value the response DTO shows, a part of an embedded value it carries, a `@ref` path, the
    values of a joined row the response carries whole (up to three relations deep), the key, and the `@sort` default.
    Never `@password`, `@writeonly` / `@nooutput`, `@jsonignore`, a `@Mask` value, a `@view` without read, or a list.
    `@sensitive` and `@encrypt` values are shown, so they sort.
  - The answer is the one an unknown property gets, so a hidden property cannot be told from a missing one. MyBatis and
    MongoDB now answer `no-such-property` for unknown terms too (they said `bad-request` before).
  - Java and Kotlin, JPA, MyBatis and MongoDB, every architecture.
- **MongoDB cleans the `html` of the members a document embeds** (#314). Under `mode: mongo`, a member kept inside
  its holder's document (an order's line) got a `cleanHtml()` that nothing called: `<script>` and `on...` handlers
  were stored as the request sent them, with no warning. It affects MongoDB projects, Java and Kotlin, with an `html`
  field on an embedded member; JPA and MyBatis are not affected.
  - The holder's CoreService now cleans each such member on every write (save, update, update by condition, and the
    batch update), after the holder's own `cleanHtml()` and before `beforeSave`. Members those members hold are
    cleaned too.
  - Members that hold each other (a line's parts holding lines) cannot be reached to any depth by the generated code:
    an `html` field among them now stops the build, naming the cycle.

### New features

- **`testCode: "contract"` grows** (#295):
  - **Callers your own code makes.** A sign-in entity whose API takes no create (sign-up by mail, social sign-in) left
    no caller to sign in, so no `@access` test was written. Write one member in your support class, and the tests of
    `@access` are written:
    ```java
    protected Map<String, Object> newSignInRow(String role) throws Exception {
        // a member of that role, made your way
        return obj("email", email, "password", "Secret-1", "memberId", id);
    }
    ```
    Kotlin: `protected fun newSignInRow(role: String?): Map<String, Any?>`. The generated `signIn()` and
    `signIn(role)` sign that row in through the generated sign-in. Without it, the summary says what to write, with
    your entity's names. It is a plain method of your class, not an interface, and without it the build is as before.
  - **Rows made without their owner.** Where nobody can be signed in, an `@owner` entity's rows are made by the
    application itself. A 5xx, or an exception your code throws, on such a row now aborts the test with the reason
    instead of failing it, and the summary names each such entity.
  - **`@Mask` and `@encrypt`.** The read and the search show the value masked; an update that sends the masked text
    back keeps the stored value, and a new value replaces it; an encrypted column holds no plain value and decrypts to
    the value sent; with `@search(eq)` a search by the value finds the row.
  - **The export.** The file holds the search's rows in its order, and a request above `elasticore.export.max-rows`
    is refused with 400 `export.too-many-rows` before anything is written.
  - In Java and Kotlin, JPA, MyBatis and MongoDB. A model without `testCode: "contract"` generates the same.

### Changes

- **The merge base is now `.elasticore/generated-base.zip`** (#312). The file that holds what the generator last
  wrote, the base every edit of a generated file is merged against, was named `.elasticore/cache`. The name read as
  disposable, and a project that deleted it or put it in `.gitignore` lost its merge. Same bytes, new name.
  - Beside it: `.elasticore/.gitattributes` (`generated-base.zip binary -filter`, so a project's `*.zip filter=lfs`
    does not touch it) and `.elasticore/.gitignore` (`!generated-base.zip`, against a project's `*.zip`).
  - **An existing project:** the first build that writes (`elcore3`) writes the new file, reads it back, updates
    `.gitattributes`, then deletes the old file, and prints
    `[elcore3] .elasticore/cache was renamed to .elasticore/generated-base.zip - commit both changes (the delete and the new file)`.
    Commit the delete and the new files together. Your edits of generated files are merged across the rename.
  - **Both files there** (a branch that had not moved yet brought the old one back): the new one is read, and every run
    says `.elasticore/cache is no longer read - ... delete .elasticore/cache and commit the delete`. The env guide 9-2
    says how to merge such a branch.
  - A run that writes nothing (`elcoreValidate`, `elcoreMigrationCheck`, `-PlistRules`) moves nothing. The build's
    words `the cache is missing` and `SKIP(not in the cache)` are unchanged.
- **The sort check is on by default in the 3.0 code.** A request that sorted by a value its response does not show is
  now 400. The runtime (`elasticore-springboot3` / `-springboot4`) has to be the plugin's version, as always: the
  generated search DTOs override `sortableProperties()`, which the runtime declares from this version on. The
  runtime's `SortableObject` checks nothing for code that does not override it (2.x DTOs), exactly as before.

### Bug fixes

- **A hand-written member's Javadoc stays with it in the merge** (#295). When the DSL added a member next to one you
  wrote, the new generated member could land between your Javadoc and your method. In the body of a Java or Kotlin
  file, the merge now keeps your insertion whole (comments, annotations, method) and puts the generated member beside
  it. A file you did not edit is still the generated file byte for byte; YAML and other text merge as before.
- **The warning for rules the selection does not carry gives advice that fits** (#247). A domain that declares
  `@access`, `@owner`, `@password`, `states:`, `@stamp`, `@deleted`, `@snapshot` or `@compute` without the rule set
  for it is warned, and the warning always said to declare an architecture, which changes nothing when env.yml's
  `publisher.rules` replaces the bundle. It now says what to do for where the selection came from: the env.yml list
  (use `rules = [...]` in the `elasticore { }` block, or name the rule set in the list), a list naming
  `jpa-springboot` or `output = 'v2'` (move to the 3.0 code), a layered bundle, or MongoDB. The build's
  `-Delasticore.publisher.rules`, which went unchecked, is now checked too. Still a warning.

### Compatibility checks

- A model that uses none of these generates the same, except the sort check of the 3.0 search DTOs and the renamed
  merge base listed above. The 2.x-compatible output is unchanged: `elcoreRulesCheck -Pstrict` reports 0 DIFF and
  `elcoreTreeCheck` 0 differ / 0 missing / 0 extra.
