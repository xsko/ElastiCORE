The tenth release candidate of 3.0: `@expose(methods)` to say which endpoints an entity's controller serves, a
root's reference to its own kind by its id, and fixes.

### New features

- **`@expose(20, methods="read,search")` lists the endpoints an entity's controller serves.** The names are `create`,
  `read`, `search`, `update` (`PUT /` and `PUT /batch`) and `delete` (`DELETE /{id}` and `POST /delete`); the rest is
  not generated. `GET /schema/info`, commands and sign-in stay. The TypeScript client calls only those, and the
  hexagonal and DDD use case drops the writes not served; the service keeps every method. Quote the list: unquoted,
  only its first name is read. An unknown name, a write listed beside `@readonly`, or another parameter of `@expose`
  is a DSL warning - a typo serves fewer endpoints, never more. Without `methods` the output is unchanged.
- **A generated controller you edited that still maps an endpoint the DSL took away** gets a DSL warning naming each
  such endpoint, for `@expose(methods)`, `@readonly` and `@restExclude` alike.

### Changes

- **`@restExclude` is deprecated.** It still applies; each entity using it gets a DSL warning naming the
  `@expose(methods="...")` list that serves the same endpoints, or the nearest one and what it changes.
- **A 3.0 TypeScript client imports only what its functions read.** A client whose server leaves endpoints out
  (`@readonly`, `@restExclude`) no longer imports the key DTO of a delete it does not have, which a client compiled
  with `noUnusedLocals` refused. A client with every endpoint is unchanged.
- **Under the DDD reference rules a root's reference to its own kind is by its id**, like a reference to any other
  root (`parent: Comment` on the root `Comment` becomes `parentCommentId`, with `parent` read-only). The table and its
  foreign key do not change, and `referenceColumn: short` does not rename the column. What changes for a project with
  such a root (`architecture: ddd` or `hexagonal`):
  - A DTO field declared under another name, such as `parentKey: long @ref(parent.commentId)`, comes out as
    `parentCommentId`, so the API property is renamed and a client still sending `parentKey` is ignored. Use the id
    field's name, or mark the relation `@objectref` to keep the object and the declared name. The ddd templates'
    `CategoryDTO.parentCatId` is `parentCategoryCatId` now.
  - A parent id that names no row answers 404 `reference.<Entity>.<relation>` before the save, not the foreign key's
    409.
  - The save is flushed and read back; until then `getParent()` is `null`.

### Bug fixes

- **The project DDL of a Kotlin entity has the foreign key of a relation referenced by its id.** The Kotlin
  relation written `final var` was not read, so its foreign key was missing; a project writing migrations gets one
  that adds them.
- **The pet store's committed schema files** say `credit_card_type VARCHAR(4)`, as the generator writes since rc9.

### Compatibility checks

- The 2.x-compatible output is unchanged. `elcoreRulesCheck -Pstrict` reports 157 MATCH / 0 DIFF / 2 ACCEPTED, and
  `elcoreTreeCheck` reports 0 differ / 0 missing / 0 extra.
