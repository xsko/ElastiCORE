The seventh release candidate of 3.0: fixes.

### Bug fixes

- **A unique value already taken, on MyBatis, answers 409 `unique`, as on JPA.** It answered `already-exists`. When the
  database reports the duplicate (the cause is an `SQLException`), the answer is the integrity violation, without the
  driver's text. A `DuplicateKeyException` your own code throws still answers `already-exists`.
- **`-PddlBaseline` over a Flyway history of your own:**
  - The state records the names of the foreign keys and indexes it takes over (`takenOver`). The database may call them
    otherwise - Hibernate names a key by a hash and holds a unique index as a constraint - so a migration that drops
    such a name, or makes it again, writes that statement as a comment to review, with the reason. Before, removing a
    relation wrote `DROP CONSTRAINT fk_...` for a name the database did not have, and Flyway stopped the application.
  - A change on SQL Server that drops and makes again an index or a key by such a name waits on SQL Server only; the
    other databases of the same history run it as written. A database added after the baseline starts from the model,
    by its names, and runs these statements as written (`takenOverOn`).
  - A history straight in `db/migration` (Spring Boot's default location) is no longer written over. Before, the first
    run wrote `db/migration/{db}/V..__init.sql` beside it, which Flyway reads too, and the application did not start.
    Now the build stops and says to run `-PddlBaseline`, which writes only the state. With more than one database, such
    a history is refused, also after the baseline: Flyway would run each database's migrations on the other.
  - A state written by `-PddlBaseline` before this release has no `takenOver`. While the database matches the model,
    delete `schema-state.json` and run `./gradlew elcore -PddlBaseline` again.
- **The first merge of a project moving from 2.x to 3.0 code no longer conflicts on custom blocks.** A stamped file's
  `// !---------- ... // ------------!` blocks are left out of the merge, as they are out of the hash, and put back where
  2.x puts them on a rewrite. A file whose blocks would not come back whole (two import blocks, a code block above the
  imports, a block never closed) merges them as edits where they stand, as before. A file the DSL does not change keeps
  its blocks where they are.
- **Ossie export:**
  - It can be used with the 2.x code (`output = 'v2'`, `rules = ['ossie-export']`), including multi-module builds.
  - A unique key's columns are the dataset's columns, also when the `@Index` names a property or a column written with
    `@column` in upper case. A key from `@unique` and an index on the same column is written once.
- The line about a kept class names the developer's file in the project, also when the project is reached through a
  link.

### Documentation

- The migration guide says that 2.x writes `withJoinFetches()` into every CoreService.
- The env guide (9-1) covers the names `-PddlBaseline` takes over and the history in the default location; 9-2 covers
  custom blocks on the first merge.

### For contributors

- **Merge gates on the lines a change writes:** `./gradlew prCheck` runs the format check (palantir-java-format;
  `./gradlew formatChanged` fixes it), Error Prone, coverage (80% of the changed library lines) and mutation testing
  (70% of PIT's mutations on them). CI runs the same gates, with bars a pull request cannot lower. CONTRIBUTING.md has
  the details.

### Compatibility checks

- The 2.x-compatible output is unchanged. `elcoreRulesCheck -Pstrict` reports 157 MATCH / 0 DIFF / 2 ACCEPTED, and
  `elcoreTreeCheck` reports 0 differ / 0 missing / 0 extra.
