The sixteenth release candidate of 3.0: two things a project moving from 2.x to the 3.0 code ran into - table names
with `table.prefix` and `@table`, and `clob` on PostgreSQL.

### Bug fixes

- **`table.prefix` comes before an `@table` name, as in 2.x.**
  - With `table.prefix: el_` and `@table(note)`, 2.x maps the entity to `el_note`.
  - Earlier 3.0 release candidates mapped it to `note`. Generation and compilation passed without a warning, and the
    application then failed at run time (`relation "note" does not exist`).
  - The JPA entity, the MyBatis SQL, the reserved-name check and the Ossie model now all name the table as 2.x does.
  - An `@table` that already starts with the prefix maps to a table with the prefix twice (`@table(el_def)` is
    `el_el_def`), as in 2.x. The build warns about it and says how to write the name.
- **`clob` and `blob` keep the value in the row.**
  - They were `@Lob`, which PostgreSQL stores apart as a large object, leaving only its number in the column. SQL
    could not read the value, and `ddl-auto: validate` refused a `text` column.
  - They are now the database's long text and binary:

    | Database | `clob` | `blob` |
    |---|---|---|
    | PostgreSQL | `text` | `bytea` |
    | Oracle | `CLOB` | `BLOB` |
    | SQL Server | `VARCHAR(MAX)` | `VARBINARY(MAX)` |

  - On SQL Server, `VARCHAR(MAX)` is how Hibernate maps long text. Use a UTF-8 collation (SQL Server 2019+) to store
    any language.
  - The build and `elcoreMigrationCheck` warn about a `String` with `@Lob` in the project's code, such as one added by
    hand to a 2.x file.

### Compatibility checks

- The 2.x-compatible output is unchanged: `elcoreRulesCheck -Pstrict` reports 158 MATCH / 0 DIFF / 2 ACCEPTED, and
  `elcoreTreeCheck` 0 differ / 0 missing / 0 extra.
- On Oracle, PostgreSQL and SQL Server, values written to `clob` and `blob` through Hibernate read back unchanged with
  plain SQL.
