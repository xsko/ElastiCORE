From this release, the 3.0 line takes features as well as fixes. This release brings the features developed since
3.0.261119, all opt-in:
- a label in other languages
- `@encrypt` and `@Mask`
- MongoDB in Kotlin
- `runtimePackages`
- `@signin(refresh=password)`

It also fixes models where `elcore3` succeeded and the build after it failed: `archTest` over the layered code, a
Kotlin build naming a Java bundle, a switch between Java and Kotlin, the Kotlin gRPC client, `publisher.rules` as a
map, and the Apache Ossie export's unique keys.

### New features

- **`@encrypt`: a column kept encrypted, and found by equality.** `phone: string(20) @encrypt @s(eq)`.
  - The runtime (both runtime libraries, `io.elasticore.springboot3.crypto`) encrypts with AES-256-GCM, with a
    random IV per write.
  - The key is `elasticore.crypto.key`. Older keys, `elasticore.crypto.keys.v1` and so on, are still read after a
    rotation.
  - With `@search(eq)` the value is found through a blind index column.
  - JPA through a converter, MyBatis through a type handler. Annotation guide, `@encrypt`.
- **`@Mask(MaskType.PHONE)`: a response field written masked.** Types: `PHONE`, `EMAIL`, `NAME`, `PLATE`, `CARD`,
  `RRN`.
  - A Jackson module of the runtime, Jackson 2 on Spring Boot 3 and Jackson 3 on Spring Boot 4, writes the masked
    value.
  - It is named in env.yml as any other annotation, `@env:maskphone`, and goes on the DTO field.
  - Only the response is masked: the entity keeps the value, and a request is read as sent.
- **MongoDB in Kotlin:** `mode: mongo` with `language = 'kotlin'`, layered, from the new bundle
  `mongo-springboot-kt`. It is the same code as the Java one, in Kotlin. Sample: `elasticore-template-kt-mongo`.
- **`elasticore { runtimePackages = [...] }`** generates the code against your own copy of the runtime.
  - The runtime's package prefixes are rewritten in the generated Java, Kotlin and resources, before the
    generated-file merge.
  - For a project that may not ship an ElastiCORE jar.
- **`@signin(refresh=password)` ends the sessions opened before a password change.**
  - It does everything `refresh=request` does.
  - The session also holds a stamp of the password hash: 16 hex characters of its SHA-256, never the hash. A
    session whose stamp is not the row's ends.
  - The session that changes the password keeps going, and so does an administrator's.

- **A label in other languages: `@label(en=Unit cost, ja=単価) -- 단가`.**
  - The `--` text stays the label. Each `language=text` pair in an `@label` you write is that label in another
    language, on a field line and on a `meta:` line (entity, DTO, enumeration). The key is a language tag, read in one
    form (`pt_BR` is `pt-BR`). A value runs to the next comma, apostrophes included; quote it when it holds a comma.
  - Generated, only when a translation is written:
    - `i18n/<domain>-labels.properties` and one `<domain>-labels_<language>.properties` per language, beside the
      message bundle, for a domain with an API. Keys are `Item` and `Item.unitCost`. Spring's `MessageSource` reads
      them by the request's `Locale`.
    - `labels: { en: "Unit cost", ja: "単価" }` in the field's entry of the TypeScript client's `XxxFields`.
    - In the Apache Ossie export, the translations become the field's and the dataset's `ai_context.synonyms`, so a
      question in that language finds the field.
  - Works in every mode (JPA, MyBatis, MongoDB), in Java and Kotlin, and in every architecture.
  - The `@label` the loader builds from `--` is never read as translations: `-- sum = price * qty` stays a label.
  - Before, `@label(en=...) -- 단가` lost the label from every output. A model without a translation generates what
    it did.
  - DSL guide 2, "A label in other languages".

### Changes

- **`archTest: true` also checks the packages your own code adds under the base** (`domain.policy`,
  `infrastructure.mail`, `adapter.in.mq` ...). Each is placed in a layer by its first segment after the base, so a
  domain policy that imports an SMTP sender now fails the test.
  - Upgrading: a test nobody edited takes the wider lists on the next build, so it can now fail where your own code
    crosses a layer. A package it cannot place (`config`) is a DSL warning.
- **The generated process manager base's comment** says what an event added to `on` does now: an empty `handle(...)`
  in your class, merged into your edits. A regenerated `XxxProcessManagerBase` changes in its Javadoc only.
- **An `@extend(Parent)` that names no Entity or DTO of any domain is a DSL warning**, as an unknown field type
  already was:
  `[shop] Order: unresolved @extend parent 'Base' - no matching Entity or DTO found in any domain`.
  - `elcoreValidate -Pstrict` fails on it.
  - Generated code is the same.
  - A parent that is your own class, named by its simple name, now warns; name it by its full class name.

### Bug fixes

- **`archTest: true` over the layered code** wrote the hexagon's rules, which the generated layered services break.
  A layered domain now gets rules that fit it:
  - `servicesDependOnNoWeb`
  - `persistenceDependsOnNothingAbove`

  ddd and hexagonal domains get the same rules as before. A `<Domain>ArchitectureTest` nobody edited takes the new
  rules on the next build, and an edited one is merged.
- **A Kotlin build whose domain names a Java bundle stops before it writes a file.** Before, it wrote `.kt` files
  holding Java and Lombok, which only `compileKotlin` found. The message names the Kotlin bundle to use instead (for
  example, `jpa-springboot-v3` becomes `jpa-springboot-kt`).
- **Switching `language` between `java` and `kotlin` removes the old language's generated files**, if they are
  unedited. Before, they were kept, and the build failed on every class declared twice. An edited one is kept as
  before, and its warning says the class is now declared twice.
- **The Kotlin gRPC client escapes its Spring placeholders.** It now writes `"\${grpc...}"`, which Kotlin parses. The
  port guide has a "Build setup for gRPC" section:
  - the protobuf plugin 0.9.4, protoc 3.25.1 and grpc 1.60.0
  - running `generateProto` after `elcore3`
  - the client's properties
- **A `publisher.rules` map with no key for the run takes the default rules** instead of stopping with
  `Unknown rule set '{ts=[ts-model]}'`. A Java build can now choose its TypeScript rules in `env.yml`
  (`rules: { ts: [...] }`).
  - A key that no run reads (`java:`, `kts:`) is a DSL warning.
  - `ossie-export` named only under `ts:` no longer turns the export on, because it is a server-side rule set.
- **The Apache Ossie export leaves out a unique key that holds a column it leaves out** (`@password`, `@writeonly`,
  `@sensitive`), with an `[ossie]` warning. Ossie's validator refuses a unique key that names a field the dataset does
  not have.

### Documentation

- The rule guide shows the one form `publisher.rules.kt` and `.ts` are read in: `rules: { kt: [...], ts: [...] }`.
- The rule guide, the DSL guide and the rule sets' comments say what a command or an event added later gets:
  - a command gets a stub that throws (Java `UnsupportedOperationException`, Kotlin `TODO`), so it answers 500 until
    the rule is written
  - an event gets an empty `handle`

  Both are regenerated while untouched and merged into your edits.

### Compatibility checks

- A model that uses none of these generates the same, and the 2.x-compatible output is unchanged:
  `elcoreRulesCheck -Pstrict` reports 0 DIFF and `elcoreTreeCheck` 0 differ / 0 missing / 0 extra.
