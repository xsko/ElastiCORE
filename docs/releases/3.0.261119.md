The first stable release of 3.0, after eighteen release candidates. From this release on, what the 3.0 code generates
changes only when a project asks for it - in the DSL or a setting - and 3.0 is supported for three years, until
2029-11-19, from the `release/3.0` branch ([SECURITY.md](../../SECURITY.md), [BRANCHING.md](../../BRANCHING.md)).

Since rc18: a GraphQL API beside REST, MongoDB on the 3.0 code, an html field kept safe before every write, a signed-in
session that follows its row, and the generated access checks read from Spring Security.

### New features

- **A GraphQL API beside REST: `graphql.enable: true`** (#148).
  - Every entity the REST API serves gets a `<Entity>GraphQlController` (a root under ddd and hexagonal), in Java and
    Kotlin, over JPA and MyBatis: `member(memberId)`, `members(search)`, `createMember`, `updateMember`,
    `deleteMember`, and one mutation per lifecycle command. They call the service the REST controller calls, so
    access, validation, invariants, `@deleted` and the lifecycle hold as they do for REST.
  - The schema is written by the build from the compiled classes (`elcoreGraphQl`, before `processResources`), into
    `src/main/resources/graphql/`, and built once: a type or operation named twice, or a schema that does not build,
    stops the build.
  - Refusals are GraphQL errors carrying the REST status and code. `mutations: false` serves queries only.
  - Not yet: subscriptions, a cursor page, a TypeScript client for the GraphQL operations.
- **MongoDB on the 3.0 code: `mode: mongo`.**
  - The bundle `mongo-springboot`: the DTOs, search, controller, access checks, `@deleted`, validation and API errors
    of the JPA bundle, with `@Document` entities, `MongoRepository`, searches as `Criteria`, a to-one relation stored
    as its id (`@DocumentReference(lazy = true)`), an entity without a collection of its own embedded, and a `long`
    key from a counter collection.
  - Checked over HTTP on a real MongoDB 7.0 (the new sample `elasticore-template-mongo`).
  - Layered Java only. Not yet: Kotlin, ddd and hexagonal over MongoDB, transactions, `@count`, `@onDelete`.
- **An html field: `content: html! @safe(basic) @plain(contentText)`** (#183).
  - Before every write - a save, an update, an update by condition, a lifecycle command - the field is kept to a jsoup
    allow-list (`@safe(basic)`, the default, or `@safe(relaxed)`), and `@plain` writes its text without tags to a
    long text field for search and previews.
  - v3 and Kotlin, JPA, MyBatis and MongoDB. An application with an html field adds `org.jsoup:jsoup`.
- **`@signin(refresh=request)`: a signed-in session follows its row** (#205, #211).
  - The member is read again on each request: a role given or taken away holds from the next request, not the next
    sign-in, and a member whose row is gone (or kept under `@deleted`) is signed out. JPA, MyBatis and MongoDB.
- **`SpringSecurityCurrentUser`: the generated `@access` / `@owner` checks read who is asking from Spring Security**
  (#210).
  - `SpringSecurityCurrentUser.of(auth -> customerIdOf(auth.getName()))`, or a token claim:
    `SpringSecurityCurrentUser.of(SpringSecurityCurrentUser.claim("customer_id", Long::valueOf))`.
  - `hasRole("ADMIN")` holds for `ROLE_ADMIN`; nobody signed in, or an anonymous authentication, is a visitor.
  - Opt-in: the application declares it as its `CurrentUser` bean; nothing is auto-configured.

### Bug fixes

- **`schema.yml` names the columns the entity maps** (#203, #204): a reference's column follows `referenceColumn` and
  `@column`; a `BigDecimal`, `Instant`, `Money` or other value field is a column, not a relation; a collection names
  no made-up column.

### Documentation

- The annotation guide shows signing in from your own code and a password reset by mail, as code the pet store runs
  (#206), and Spring Security instead of `@signin`: form login, JWT and OIDC.
- The README, the tour, SECURITY.md and BRANCHING.md say 3.0 is released and until when it is supported.

### Compatibility checks

- A model that uses none of these generates the same, and the 2.x-compatible output is unchanged:
  `elcoreRulesCheck -Pstrict` reports 0 DIFF and `elcoreTreeCheck` 0 differ / 0 missing / 0 extra.
