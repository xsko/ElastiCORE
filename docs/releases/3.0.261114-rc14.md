The fourteenth release candidate of 3.0: three things a project moving from 2.x to the 3.0 code ran into - the search
result DTO, the order of the generated API errors beside an application's catch-all, and the imports a preserved block
needs.

### Bug fixes

- **`@searchResult(Entity)` answers the 3.0 search.** The DTO was generated but unused: the search returned the
  entity's full DTO, so a list carried every column (a large text column with it). The search now returns the result
  DTO (`Page<EntityResultDTO>` or a list), the mapper has `toEntityResultDTO`, and the controller, the hexagonal use
  case and the TypeScript client use it - layered, ddd, hexagonal, Kotlin and MyBatis. The 2.x-compatible output for
  such a model now matches the 2.x generator too.
- **A generated `XxxApiErrors` comes before an application advice without `@Order`.** It was
  `@Order(LOWEST_PRECEDENCE)`, the same as an advice without an order, so with an application
  `@ExceptionHandler(Throwable.class)` Spring's choice between them was not set and a generated controller's 404 could
  answer 500. A new (or never edited) `XxxApiErrors` is `LOWEST_PRECEDENCE - 1`; for an edited one, `elcore3` and
  `elcoreMigrationCheck` warn and name both files.
- **The imports a preserved block may lose are said.** Code in a preserved block keeps its lines when a file is
  rewritten, not the 2.x wildcard imports above them. `elcoreMigrationCheck` lists those imports, and the build warns,
  so they can go into the preserved block under `package` before the code fails to compile.

### Compatibility checks

- The 2.x-compatible output is unchanged for a model that uses none of these. `elcoreRulesCheck -Pstrict` reports
  158 MATCH / 0 DIFF / 2 ACCEPTED, and `elcoreTreeCheck` 0 differ / 0 missing / 0 extra.
