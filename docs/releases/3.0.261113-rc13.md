The thirteenth release candidate of 3.0: moving a project 2.x generated to the 3.0 code - a check that says beforehand
what the first 3.0 build will do, a repository without a service or an API, and three things such a move ran into fixed.

### New features

- **`./gradlew elcoreMigrationCheck`: the first 3.0 build of a project 2.x generated, with nothing written.** It runs the
  build `output = 'v3'` would run - the 2.x code read as the bases of the edited files, the merge, the removal of what is
  no longer produced - holds back every write, delete and the cache, and writes `build/elasticore/migration-check.md`:
  the generated files the build removes or no longer writes that your code still uses (by name, or a repository through
  the domain helper's `helper.getXxx()`), with the DSL to write instead; the files that would conflict, be kept as yours
  or be left as the 2.x code; the imports a merge would take out that your code may need; and what an older generator
  wrote that the 3.0 code does not. The console prints each file's status as the build will. Java projects only. The
  migration guide walks through the move step by step.
- **`meta: entity @repository`**: the entity gets its repository and the domain helper's getter (`helper.getXxx()`),
  and no service, controller or API - for a table code of your own reads and writes. 3.0 JPA output, Java and Kotlin;
  under `mode: mybatis` it is a warning for now.

### Changes

- **Korean guides already in the blueprint stay Korean** when `elasticore { guides }` is not set, and the build says so
  (`guides = 'en'` switches them). Before, the next build replaced them with the English ones silently.

### Bug fixes

- `output = 'v2'` on Spring Boot 4 compiles: the 2.x-compatible `delete(SrchDTO)` called
  `JpaSpecificationExecutor.delete(Specification)`, which Spring Data JPA 4 does not have. On Boot 4 it now reads the
  rows and removes them one by one (so `@PreRemove` and cascades run). Spring Boot 3 output is unchanged.
- The generated-file merge keeps a 2.x wildcard import (`import ...dto.*;`) that code you wrote into the file relies on,
  while the generated code still imports from that package. Before, it was dropped and the file failed with
  `cannot find symbol`.

### Compatibility checks

- The 2.x-compatible output is unchanged for a model that uses none of the new features. `elcoreRulesCheck -Pstrict`
  reports 158 MATCH / 0 DIFF / 2 ACCEPTED, and `elcoreTreeCheck` 0 differ / 0 missing / 0 extra.
