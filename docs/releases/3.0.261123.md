This release brings the features developed since 3.0.261121. They are opt-in, except two additions to the
generated output that are listed under Changes:
- role names in `@access`, joined with `|` and `&`
- `testCode: "contract"`: generated tests of what the DSL declares
- a search exported as a CSV file or an .xlsx workbook, with enumerations by their label if you ask
- refusal messages that name the field, the entity and the state by their labels
- labels for screens, and enumeration labels in every language for the TypeScript client and the Apache Ossie export

It also fixes a masked field that an update wrote over, a `@pattern` whose quoted expression holds an `=`, and three
gaps in the rule API for team rules.

### New features

- **`@access` takes role names, joined with `|` (either) and `&` (both)** (#269).
  - `read=owner|MANAGER`: the owner, or a MANAGER on every row. A MANAGER's search is not narrowed; anyone else's
    search returns their own rows.
  - `update=REP&owner`: a REP on a row of their own. An owner who is no REP is refused with 403.
  - `close=REP&owner|MANAGER`: `&` binds tighter than `|`. There are no parentheses. Spaces around `|` and `&` are
    allowed.
  - A role name is a constant of the `@signin` entity's role field (`@role`, or the field named `role`). A word that
    is a level (`public`, `user`, `owner`, `admin`, `none`) is that level, in any case. Any other word is a role name
    and starts with a capital letter.
  - The administrator passes every entry except `none`.
  - Works in every mode (JPA, MyBatis, MongoDB), in Java and Kotlin, and in every architecture: the service checks of
    create, read, update, delete, search and the commands, the per-row read, and the search filter.
  - When the role field is an enum, a role name that is not one of its constants stops the build:
    `[Shop] Ticket @access(create=REP|MANGER): MANGER is neither a level (public, user, owner, admin, none) nor a constant of the role enum UserRole (USER, MANAGER, REP, ADMIN).`
    With a string role field, or no `@signin`, a name is not checked.
  - DSL warnings: a role constant named `PUBLIC`, `USER`, `OWNER` or `NONE` (`UserRole.USER cannot be named in
    @access`), and `&` with `user` or `public` (adds nothing) or with `none` (lets nobody in).
  - The sign-in is still generated only when the `@signin` entity's update lets in only the row's own user and the
    administrator. `update=owner|MANAGER` is refused, with the reason; `update=REP&owner` is not.
  - The Apache Ossie export writes a joined entry as written (`owner|MANAGER`).
  - An entry of one level generates and behaves as before. For code that calls the runtime,
    `AccessPolicy.level(op)` returns null for an entry that names a role or joins words.
- **`testCode: "contract"`: tests of what the DSL declares** (#295). Set `config.testCode: "contract"` in env.yml.
  - Per domain you get `<Domain>ContractSupport` and a `<Entity>ContractTest` for each entity whose API creates rows,
    in `src/test/java` (`src/test/kotlin` for Kotlin). They are written once, then merged when the DSL changes, and
    your edits are kept.
  - The tests call the project's own API and check the status and the problem's `code`, never the message text.
  - Every v3 output (Java and Kotlin), every architecture, JPA, MyBatis and MongoDB. The 2.x output gets none, with a
    DSL warning. `testCode: "true"` means what it did.
  - Lifecycles: each move of `states:` from each state it lists (2xx, the new state, a `@stamp` set), refused with 409
    from every other state a row can reach; a new row starts in each lifecycle's `initial`.
  - Constraints, at the bound and one past it: `!`, `string(n)` and `@length`, `@min` / `@max`, `@pattern`,
    `@minsize(n)`, and `@invariant` of the forms `field > n` (`>=`, `<`, `<=`, `==`), `items.size > n`, `notNull`,
    `notEmpty`.
  - Bean Validation marks: `@notblank`, `@email`, `@past` / `@pastorpresent`, `@future` / `@futureorpresent`. Dates
    are taken from the clock when the test runs.
  - `@pattern` with lookaheads, the usual password rule, such as `^(?=.*[A-Za-z])(?=.*[0-9]).+$`.
  - `@access`: each operation is tested at the level its entry gives it. A caller each term lets in passes; a visitor
    is refused with 401; a caller of a role no term lets in, 403; where `owner` is a word, a caller on another's row,
    404. The support class signs in principals of a role: `signIn(role)`, `sentBy(caller, ...)`, `assertAllowed`,
    `assertDenied`, `assertFinds`, `assertMisses`.
  - Rows are built from the model, and each test makes its own rows. Over JPA and MyBatis the tests run on an
    in-memory H2 of their own and each test's rows are rolled back. Over MongoDB they run on the server
    `ELASTICORE_IT_MONGODB_URI` names, and are skipped without it.
  - A refusal the model declares, or a 5xx, fails a test. A refusal by your own application code aborts it, with the
    reason.
  - What cannot be tested is counted, with the reason, after the run's summary:
    `=== contract tests: 70 written, 2 skipped (Receipt: its API takes no create (@expose methods), so no row is made to test; Product.price @min(0): @invariant(price > 0) refuses the boundary) ===`
  - The build never breaks: if your edited support class lacks a member the new tests call, those tests are not
    written, and the summary names the members to add.
  - No build file is changed. The tests need `spring-boot-starter-test`, H2 over JPA and MyBatis, and on Spring Boot 4
    `spring-boot-starter-webmvc-test`.
  - Not yet tested: `@Mask`, `@encrypt`, `export`, a lifecycle's `delete:` states, and an aggregate member's own
    constraints.
  - Env guide 6.2.
- **A search exported as a CSV file or an .xlsx workbook** (#271). List `export` in `@expose(methods="...")`, for
  example `@expose(methods="read,search,export")`.
  - The controller gets `POST /api/<domain>/<entity>/export`, taking `{ search, sortCode, columns, headers, format }`,
    all optional. It reads every page of the search, so the conditions, the search's `@access` and the `@owner` filter
    are the search's.
  - Columns are the response DTO's properties, as the JSON shows them (`@Mask` masked, money and dates as written), or
    the ones `columns` lists. Titles are `headers`, else each column's label in the request's language, else the name.
  - CSV by default: UTF-8 with a BOM, RFC 4180 quoting, CRLF, and a `'` before a text that starts with `=`, `+`, `-`,
    `@`, a tab or a carriage return (CSV injection).
  - `.xlsx` for `"format": "xlsx"` or an Accept header that asks for it, when the application has Apache POI;
    otherwise 406. Numbers are numbers, dates are dates, and text is never a formula.
  - `elasticore.export.max-rows` (default 100,000): a larger result is refused with 400 `export.too-many-rows` before
    anything is written.
  - The TypeScript client gets `exportXxx(body: ExportRequest<XxxSrchDTO>): Promise<Blob>`.
  - Every mode (JPA, MyBatis, MongoDB), Java and Kotlin, every architecture. The runtime adds no dependency (POI is
    yours to add).
- **An export writes an enumeration by its label** (#289). Add `"labels": ["status"]`, or `"labels": "*"` for every
  enumeration column, to the export's body.
  - The label is in the request's language, from the label bundle; else the bundle's default file; else the
    enumeration's own label column; else the code.
  - A name that is not an enumeration column of the export is refused with 400 `export.labels`.
  - A body without `labels` writes what it did. The TypeScript client's `ExportRequest` gets
    `labels?: string[] | '*'`.
- **Refusal messages name the field, the entity and the state by their labels**, in the language of the response.
  - `invariant.*` messages take `{0}` the field and `{1}` the entity. `state.*` messages keep `{0}` and `{1}` (the
    codes) and add `{2}` the field, `{3}` the entity, `{4}` the current state and `{5}` the allowed states.
  - The default sentences use them, for example `{3} cannot <command> when {2} is {4}; it must be {5}`. With
    `@label(en=Order status)` on `status`, an English answer reads
    `PurchaseOrder cannot ... when Order status is SHIPPED; it must be [PLACED]`.
  - Where no label is found, a value reads as the code, so a model without labels answers word for word as before.
    A sentence written in the DSL stays as written.
  - `config: labelLanguage: ko` in env.yml (optional, for the whole domain) names the language of the `--` labels.
    The label bundle then gets a file of that language with every label.
  - Java and Kotlin, every mode and architecture that writes these refusals.
- **Labels for screens, in the TypeScript client** (#268).
  - `XxxMeta`: the DTO's own label and its translations, `{ label: "...", labels: { en: "..." } }`.
  - `validateXxxCodes(value, partial)` beside `validateXxx`: the same checks, as the server's `fieldErrors` codes
    (`NotNull`, `Size`, `Min` / `Max`, `DecimalMin` / `DecimalMax`, `Pattern`, `Email`), so a screen can say them in
    its own words.
  - An enumeration's label in other languages, as columns named `<label column>_<language>` (`name_en`, `label_ja`,
    `label_pt_BR` for `pt-BR`). The client gets `XxxLabels` beside the unchanged `XxxLabel`, and the label bundle gets
    `Enum.CONSTANT` in each language's file.
  - A column whose suffix is not a language, beside a real translation column (`name_kor` beside `name_en`), is a DSL
    warning.
- **The Apache Ossie export gives an enumeration's codes their labels in every language** (#272), from the same
  `<label column>_<language>` columns.
  - The codes text: `"Codes: PRS = 발굴 (en: Prospecting, ja: 見込み), WON = 성사 (ja: 成約), LST = 실패"`.
  - The field's `ELASTICORE` extension gets `code_labels` beside `codes`:
    `"code_labels": {"PRS": {"en": "Prospecting", "ja": "見込み"}, "WON": {"ja": "成約"}}`.
  - An enumeration without such columns exports as before. The output passes Apache Ossie main's validator.

### Changes

- **The TypeScript client gains two additions by default**, as agreed on #268:
  - `validateXxxCodes` in every DTO file that has `validateXxx`
  - `XxxMeta` in each DTO file whose type has a label (a `--` comment on the `meta:` line counts)

  Nothing else in the TypeScript output changes, and no label bundle is written for them.
- **The generated refusals of a model with invariants or lifecycles carry the labels**, and the default bundle's
  sentences of those codes are patterns that name them. The answers of a model without labels are the same, word for
  word, in English and in your translations. Existing `_ko` translations of `state.*` keep their meaning (`{0}` and
  `{1}` are still the codes).
- **A project with `runtimePackages`** (its own copy of the runtime) takes the new `Label` class and the changed
  `ErrorMessages` into its copy, and the new `export` classes with the rest.

### Bug fixes

- **An update keeps a `@Mask` field's stored value when the text sent is that value masked** (#270). Before, a client
  that read a row and sent it back (an edit form, a `PUT` of the read DTO) wrote `010-****-5678` over the phone number
  for good.
  - `PUT` and `PUT /batch` now compare the text with the stored value, masked as the response showed it. When they are
    the same, the stored value is kept. With `@encrypt` too.
  - Any other text is written as before. A create writes what it is sent.
  - JPA (Java and Kotlin), MyBatis and MongoDB (Java and Kotlin), every architecture. A model without a masked field
    generates the same code.
- **`@pattern('^(?=.*[A-Za-z])(?=.*[0-9]).+$', '...')` keeps its regular expression** (#267). An `=` inside a quoted
  string split the parameters, so the lookahead `(?=` broke the pattern, and every value was refused, on the server and
  in the TypeScript validator. An `=` inside quotes is now part of the value, and a group inside a group
  (`'^((AB|CD)-[0-9]{3})$'`) is read. An `=` outside quotes is a `key=value` pair as before.
- **`FieldSpec.blindIndexOf()` tells a team rule which field is a blind index, and of what** (#290). With
  `email: string(100) @encrypt @s(eq)`, the generated `emailBidx` looked like a declared field to a rule walking
  `fields()`. Now `blindIndexOf()` returns `email` for it, and `null` for every other field:
  `if (f.blindIndexOf() != null) continue;`. Generated code does not change.
- **A team marker's flags are kept** (#273). `@ui(menu=sales, order=30, staff)` lost `staff`. The rule API now reads
  them: `EntitySpec.metaFlags("ui")` (`[staff]`, beside `metaProperties("ui")`), `FieldSpec.dslProperties("ui")` (every
  pair in the order written) and `FieldSpec.dslFlags("ui")`. What existing readers see is unchanged.
- **A TypeScript run writes the files of a `DomainArtifactContributor` listed under `ts:`** (#266). Before, a team's
  domain-level TypeScript file was never written, with no warning. It is now written to `src/main/ts/` after
  `apiSupport.ts`. A project without its own rule writes the same.

### Compatibility checks

- A model that uses none of these generates the same (except the default changes listed under Changes), and the
  2.x-compatible output is unchanged: `elcoreRulesCheck -Pstrict` reports 0 DIFF and `elcoreTreeCheck` 0 differ /
  0 missing / 0 extra.
