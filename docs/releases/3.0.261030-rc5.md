The fifth release candidate of 3.0.

### New features

- **Generated files merge with your edits instead of being skipped.** This is the default for the 3.0 code. `elasticore { merge = false }` turns it off.
  - Every generated file is written without the `//ecd:` first line: Java, Kotlin, MyBatis mapper XML, `orm.xml`, DDL, messages, HTTP-port properties and the TypeScript client.
  - What was generated is kept in `.elasticore/cache`; commit it with the generated files.
  - The next build compares, file by file, the last generated text, the file on disk and the new text. An untouched file is regenerated. An edited file keeps your edits and takes the DSL's changes (`MERGED(your edits kept)`).
  - When both sides change the same lines, the file gets git's conflict marks (`<<<<<<< yours` / `>>>>>>> elasticore`) and the build fails until they are resolved.
  - Java and Kotlin are merged with awareness of imports and members. Measured on the 2.x template and the pet store: adding a field to every entity changed 119 files with 0 conflicts.
  - Files generated once (controllers, extension services, a split root's class, factories) follow the DSL until you edit them. After that they take only the changes that merge cleanly. When a change overlaps your edit, the file is left as it is (`KEPT(yours ...)`), the build says what to carry over, and no conflict marks are written.
  - A 2.x project that moves to the 3.0 code (`output = 'v3'`) carries its hand-edited 2.x files into the merge, when the `//ecd:` hash confirms what was generated into them. The first such build covers every domain (`-Pdomain` is refused).
  - A generated class the DSL no longer produces is kept while code that stays still uses it, and the build names that code.
- **`mode: mybatis`.** A domain whose `env.yml` says `mode: mybatis` is generated with MyBatis instead of JPA: layered Java, Spring Boot 3 and 4.
  - The DTOs, controllers, access checks and service signatures are those of the JPA code.
  - Each entity gets a mapper interface and XML. To-one relations are joined in one statement, there is a condition per search field, a whitelisted sort and paging per database, and the version is checked on update.
  - Money, Quantity, value objects (`@embeddable`), collections (`@OneToMany(mappedBy)`, written with their aggregate root) and `@joinBy` are supported.
  - Generation stops with the reason for anything not supported yet.
  - Schemas are written for H2, PostgreSQL, Oracle and SQL Server. CI runs the MyBatis pet store and the template's API tests against Oracle 23, PostgreSQL 16 and SQL Server 2022.
  - New modules: `elasticore-template-mybatis` and `elasticore-sample-petstore-mybatis`.
- **DDL and Flyway migrations for the whole project.** `elasticore { ddl { databases = [...]; migration = 'flyway' } }` turns this on.
  - It writes `db/schema-{h2|postgresql|oracle|sqlserver}.sql` for every domain, JPA and MyBatis. JPA tables are read from the generated entities and `orm.xml`, as Hibernate sees them.
  - With `migration = 'flyway'`, a model change writes a `V{time}__...sql` migration per database.
    - Additions and widenings are written as statements.
    - Anything that can lose data or fail on existing rows is written as a commented **review** block and a `REVIEW` line in the build log.
  - The JPA samples start with `ddl-auto=validate` on the generated schema. The pet store does so on PostgreSQL, Oracle and SQL Server too.
  - Projects that keep the 2.x code get the same through the new `elcoreDdl` task.

### Changes

- **The runtime libraries no longer bring `spring-boot-starter-data-jpa`.** Before, it started Hibernate inside MyBatis applications.
  - A JPA project declares the starter itself, as the README's build does.
  - Symptom when it is missing: no `EntityManagerFactory` bean, or no Hibernate, at start-up.
- With MyBatis on the classpath, the runtime tells MyBatis which database it runs on. `elasticore.mybatis.database-id=false` turns this off.
- `.elasticore/cache` is new in a 3.0-code project; commit it.

### Bug fixes

- With `mapping: xml`, a `-Pdomain` build no longer drops the other domains' mappings from the module's `orm.xml`. The classes the generated domain no longer has, or has moved, leave the file.
- `orm.xml` and the default messages file were overwritten on every build. They now merge your edits like any other generated file.

### Documentation

- The README and the tour say that editing generated code no longer stops the model's changes from coming in, and that `.elasticore/cache` is committed.

- The guides say that files generated once follow the DSL until you edit them, and what happens after that.
- The migration guide says how to roll back a project that moved to the 3.0 code: restore the sources from the commit before the move, then lower the version.
  - The 2.x generator overwrites files without the `//ecd:` stamp, edits included.
  - That covers controllers and extension services too.
- The env guide covers the merge (9-2: committing the cache, resolving conflicts, git merges), the project DDL and `mode: mybatis` (2.3).

### Compatibility checks

- The 2.x-compatible output is unchanged. `elcoreRulesCheck -Pstrict` reports 157 MATCH / 0 DIFF / 2 ACCEPTED, and `elcoreTreeCheck` reports 0 differ / 0 missing / 0 extra.
