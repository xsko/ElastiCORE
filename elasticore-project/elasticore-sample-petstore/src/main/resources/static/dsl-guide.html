Pet Store - 업무를 DSL 로

YAPS Pet Store 는 애완동물을 파는 온라인 가게입니다 (Java EE 7 pet store 를 ElastiCORE 3.0 으로 다시 만든 것). 손님은 분류(물고기·개·파충류·고양이·새) → 상품(불독·푸들…) → 품목(수컷 강아지·암컷 강아지처럼 실제로 사는 단위) 순으로 둘러보고 장바구니에 담습니다. 결제하려면 회원 가입·로그인하고, 배송지와 카드를 넣으면 주문이 접수됩니다. 금액은 품목 가격 합계에 VAT 5.5% 를 더하고, VAT 포함 금액에서 2.25% 할인합니다. 손님은 자기 주문을 보고 취소할 수 있고(배송 전까지), 가게 관리자는 백오피스에서 주문을 배송 처리하고 상품을 관리합니다.

이 문서는 그 업무를 업무 단위로 나눠, 각 규칙이 DSL 의 어디에 적혔는지, 무엇이 생성되고 무엇을 손으로 썼는지, 그리고 DSL 로 아직 표현할 수 없는 것까지 적습니다. "확인한 결과" 열은 실행 중인 애플리케이션에 HTTP 로 요청해서 본 응답입니다. DSL 과 생성 코드 발췌는 빌드 결과물에서 그대로 읽어 왔습니다.

사람과 권한

방문자

로그인 전. 상품을 보고 검색하고, 가입합니다.

고객 (USER)

가입하면 이 역할. 자기 정보와 자기 주문만 보고 고칩니다.

관리자 (ADMIN)

모든 것을 봅니다. 배송, 상품 관리, 고객 역할 변경, 삭제.

DSL 은 엔티티마다 @access(연산=수준) 으로 말합니다. 수준은 public(방문자도) · user(로그인) · owner(본인 것만, @owner(필드) 로 주인을 정함) · admin. 적지 않은 연산은 관리자만 할 수 있습니다.

2. 상품 관리 대부분 DSL

      
관리자가 분류·상품·품목·국가를 등록·수정·삭제하고 가격을 바꿉니다.


업무 규칙DSL확인한 결과


관리자만 바꾼다@access(read=public) 에 create·update·delete 를 적지 않음방문자 401, 고객 403, 관리자 200


가격은 0 보다 크다@min(0.01, 'price must be positive')0 → 400 "unitCost: price must be positive" (화면 검증 함수에도 같은 문구)


값을 바꿔도 지난 주문은 그대로주문 줄 unitCost … @snapshot(item.unitCost)10.00 → 11.50 으로 바꾼 뒤에도 기존 주문 줄은 10.00


품목이 있는 상품은 못 지운다DSL 에 규칙 없음 - DB 외래 키409 "The row is still referenced by another…"



      
DSL 밖: "품목이 남아 있으면 삭제할 수 없다" 는 업무 규칙이지만 DSL 에 쓸 곳이 없어서 DB 외래 키 오류(409)로만 지켜집니다.

4. 로그인·로그아웃 DSL 로 전부

      
고객은 로그인 ID 와 비밀번호로 로그인하고, 로그아웃합니다. 화면은 접속할 때 "지금 누구인지" 를 묻습니다.

5. 내 정보 DSL 로 전부

      
고객은 자기 이름·연락처·집 주소·비밀번호를 고칩니다. 관리자는 모든 고객을 보고 역할을 바꿉니다.


업무 규칙DSL확인한 결과


자기 것만 보고 고친다@owner(customerId) @access(read=owner, update=owner)고객 검색 결과는 본인 1건, 남의 정보 GET·PUT → 404


역할은 관리자만role … @access(admin)본인이 "role":"A" → 무시(U 유지), 관리자가 바꾸면 A


비밀번호를 바꾸면 다시 해시@password새 비밀번호로 로그인 200, 옛 비밀번호 401


탈퇴는 관리자만delete 를 적지 않음본인 DELETE → 403



      
업무에 따라 부족한 것: 비밀번호 변경이 일반 수정(PUT)이라 현재 비밀번호를 확인하지 않습니다.
        필요하면 commands: changePassword: current, next 로 명령을 선언하고 확인 로직은 행위 클래스에 씁니다.
        고객이 스스로 탈퇴하게 하려면 @access(…, delete=owner) 한 단어면 됩니다.


      
6. 장바구니 DSL 밖

      
손님은 품목을 담고, 수량을 바꾸고, 비웁니다. 로그인하지 않아도 담을 수 있고, 결제할 때 로그인합니다.

      
장바구니는 브라우저(localStorage) 에만 있습니다 (web/src/cart.ts, 손으로). 서버에는 결제 순간에 품목 ID 와 수량만 갑니다.
        화면에 보이는 가격은 안내용이고, 실제 가격은 서버가 결제 때 다시 매깁니다(7번 @snapshot).

      
DSL 밖 (의도): 결제 전의 장바구니는 업무 기록이 아니라고 보고 서버 모델에 넣지 않았습니다.
        "기기를 바꿔도 장바구니 유지" 가 업무라면 Cart·CartLine 엔티티와 @owner 로 DSL 에 쓰면 됩니다.

• 가격 정책 - 설정 값(VAT 5.5%, 할인 2.25%)을 쓰는 계산, 계산 순서, 반올림. @compute 는 필드끼리의 곱·합만 됩니다.
        이 샘플에 남은 유일한 도메인 코드입니다. 개선 후보: policy: (요율을 설정에서 읽는 계산).
        
• 기본값 규칙 - "배송지가 없으면 집 주소", "주문일은 오늘".
        
• 결제 승인·재고 - 모델에 없습니다 (원본 Java EE pet store 에도 없음). 카드사 연동은 DSL 의 port.yml(HTTP 포트)로 선언할 수 있지만 이 샘플은 쓰지 않습니다.


      
8. 주문 조회 DSL 로 전부

      
고객은 자기 주문 목록과 상세(줄·금액·배송지·카드 종류)를 봅니다. 관리자는 모든 주문을 봅니다.


업무 규칙DSL확인한 결과


자기 주문만@owner(customerId) @access(read=owner)검색은 본인 것만. {"customerId":1} 로 찾아도 0건. 남의 주문 404, 방문자 401


관리자는 전부(관리자는 모든 수준을 가짐)관리자 검색은 모든 고객의 주문


줄에 품목 이름dto.yml itemName: string @ref(item.name)줄마다 itemName ("Large")


최신순화면이 sortColumn: orderDate 를 보냄DSL 에 기본 정렬 없음



      


      
9. 주문 취소 DSL 로 전부

      
고객은 자기 주문을 배송 전(접수 상태) 에만 취소할 수 있습니다. 화면은 취소할 수 있을 때만 버튼을 보입니다.


업무 규칙DSL확인한 결과


자기 주문만cancel=owner남의 주문 → 404


접수 상태에서만states: status: cancel: PLACED -> CANCELLED두 번째 취소·배송 후 취소 → 409 "cannot cancel when status is SHIPPED; it must be [PLACED]"


취소되면 알린다@event(… Cancelled)PurchaseOrderCancelledEvent


버튼은 할 수 있을 때만(생성) TypeScript Orders.canCancel(order)서버의 canCancel() 과 같은 판단



      
모델에 없는 것: 환불. 결제 모델이 없어서 취소는 상태만 바꿉니다. 결제 상태가 생기면
        같은 cancel 명령이 두 생명주기(주문·결제)를 함께 바꾸게 쓸 수 있습니다 - 주문 생명주기 참고.


      
10. 배송 (백오피스) DSL 로 전부

      
관리자는 백오피스에서 모든 주문을 보고, 접수된 주문을 배송 처리합니다. 주문은 고칠 수 없고, 지우는 것은 관리자뿐입니다.


업무 규칙DSL확인한 결과


관리자만@access 에 ship 을 적지 않음고객 → 403 "ship PurchaseOrder is for the administrator"


접수 상태에서만states: status: ship: PLACED -> SHIPPED취소된 주문 배송 → 409


배송되면 알린다@event(… Shipped)PurchaseOrderShippedEvent


버튼은 할 수 있을 때만(생성) TypeScript Orders.canShip(order)-


주문은 고칠 수 없다@editable 이 아닌 루트 → 수정 API 없음PUT → 405


삭제는 관리자만delete 를 적지 않음고객 403, 관리자 200




      
주문 생명주기 (states:)

      

        PLACED
        →ship (관리자)
        SHIPPED
        
        PLACED
        →cancel (본인)
        CANCELLED
      

      
    
        
  • states: 바로 아래 키 status 는 필드 이름입니다 - fields: 의 status: OrderStatus.
    • 
        
  • 상태 이름(PLACED…)은 그 필드 타입인 OrderStatus enum 의 상수 이름입니다 (DB·JSON 코드 PLC 가 아님).
          enum 에 없는 이름이면 빌드가 경고하고 그 생명주기를 만들지 않습니다.
    • 
        
  • initial 은 시작 상태, 나머지 키는 명령이고 값은 시작 상태 -> 도착 상태 입니다. 명령마다 API(POST …/{id}/ship)가 생깁니다.
    • 
        
  • SHIPPED 다음은? 나가는 화살표가 없는 상태는 끝입니다. 다음 단계가 필요하면 enum 에 DELIVERED 를 더하고 deliver: SHIPPED -> DELIVERED 한 줄.
    • 
        
  • 상태 필드가 둘 이상(주문 상태·결제 상태)이면 필드마다 생명주기를 쓰고, 같은 명령 이름을 두 곳에 두면 그 명령은 둘을 함께 바꿉니다 -
          모든 생명주기를 먼저 확인하고, 하나라도 아니면 아무것도 바꾸지 않습니다.
    • 
      

      


      
업무 지표와 업무 용어 (metrics:, @terms)

      
가게가 보는 숫자 - 매출(취소 제외, VAT 포함·할인 후), 주문 수, 객단가(주문 1건 평균), 배송·취소 건수, 고객 수 -
        도 업무 정보입니다. 화면·SQL·BI 도구마다 "매출" 을 따로 정의하면 숫자가 달라지므로, DSL 에 한 번 적습니다.

      

      
    
        
  • 한 줄이 지표 하나: sum|avg|min|max|count(엔티티.필드), 조건은 where 필드 != 값 and …, 지표끼리는 revenue / orderCount.
    • 
        
  • enum 은 상수 이름으로 씁니다(CANCELLED) - 내보낼 때 저장 코드('CAN')로 바뀝니다.
    • 
        
  • @terms(…) 는 업무에서 부르는 이름·동의어입니다. 엔티티(주문 = order, purchase, 구매)·필드(가격)·지표에 붙입니다.
    • 
        
  • 애플리케이션 코드는 만들지 않습니다. Apache Ossie 시맨틱 모델의 metrics 와 ai_context.synonyms 로 나가서,
          BI·AI 도구가 "매출" 을 물으면 이 정의를 씁니다.
    • 
      

      

      
확인: MetricsTest 가 주문을 접수·배송·취소한 뒤, 내보낸 지표 SQL 을 실제 DB 에서 실행한 값과 엔티티로 직접 계산한 값이
        같은지 봅니다 (매출, 주문 수, 객단가, 배송·취소 건수, 고객 수).

      
아직 못 하는 것: 지표는 한 엔티티 안에서 셉니다. "취소되지 않은 주문의 팔린 수량" 처럼 주문 줄을 주문 상태로 거르는 지표는
        쓸 수 없어서 넣지 않았습니다 - 억지로 쓰면 취소분까지 셉니다. 기간(월별)은 BI 도구가 orderDate 로 나눕니다.
