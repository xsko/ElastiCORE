### Removals (ddd / hexagonal - `namespace.processManager`, issue 370)

- Why: completes the removal of `domainService:`, `processManager:` and `@specification` (the entry above).
  3.0 placed the process managers by `namespace.processManager`; nothing reads it in 3.1, and it was ignored without a
  word. `namespace.domainService` is different: the generated architecture test reads it as a domain package (with
  `entity`, `enumeration`, `event` and `domainRepository`), so it stays and is read without a notice.
- Before: in 3.0, `namespace.processManager: com.acme.shop.application.process` placed the generated process
  managers; with the sections removed it would have been read by nothing, without a word.
- After: the server's run says it once, under the same heading as the other removed DSL, as a notice (`DSL_NOTICE`, not

  `[shop] namespace.processManager (com.acme.shop.application.process) is no longer read since 3.1 - remove it; nothing

  Generated code does not change.

    yours now: ...`). No other TypeScript file stops being generated between 3.0 and 3.1.
  - To finish: write the replacements (the DSL guide's chapter 8 and the annotation guide's `@specification` section),
    move the code off the kept classes, delete the leftover sections, annotations and `namespace.processManager`; the

### Bug Fixes (v3 generated-file cleanup - TypeScript)

#### A stale TypeScript file that starts with an empty line no longer stops the run
- Why: found while checking that no TypeScript file is lost when it stops being generated (issue 370). A generated
  DTO with nothing to import (`XxxKeyDTO.ts`, `XxxSrchDTO.ts`, a DTO of plain fields) starts with an empty line. When
  one stops being generated - its entity or its domain removed - the stale-file pass read the empty line as a stamp and
  `elcore3ts` stopped with `java.lang.StringIndexOutOfBoundsException: begin 1, end 0, length 0` (`HashUtils.getVersion`):
  nothing after it ran, so the client was not updated and an `OrderSpecifications.ts` due to be handed over was not.
- Before: the run failed; the stale file stayed.
- After: a first line that is no stamp is read as no stamp; the stale file goes as any unedited one does
  (`REMOVED(the DSL no longer produces it)`) and the run goes on. `HashUtils` is unchanged (2.x reads it).
- Checked: `RemovedDslTest.aStaleTypeScriptFileThatStartsWithAnEmptyLineDoesNotStopTheRun` - failed with the exception
  above before the fix, passes after it; found by disabling a domain in the upgrade copy above.
- Files: `RulesGenRunner.java` (`readStatus`), `RemovedDslTest.java`.
